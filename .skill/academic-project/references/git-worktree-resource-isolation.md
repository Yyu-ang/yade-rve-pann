# Git worktree 与大型资源隔离规范

适用于本地 Git 仓库中的并行代码开发。目标是隔离可写工作区，同时避免把大型数据、依赖和构建产物重复搬进每个工作区。

## 1. 先选工作模式

- **单 Agent 顺序工作**：复用当前 checkout 通常足够；不要为了形式上的隔离额外创建 worktree。
- **多个 Agent 同时写代码**：每个并发写入者使用独立分支和独立 worktree。只说“在不同分支工作”不构成工作区隔离；同一目录被切换分支仍会互相影响。
- **运行平台已经提供独立 checkout/worktree**：先核验每个 Agent 的实际根路径、分支、HEAD 和工作树状态，不要在其隔离目录中再嵌套创建 worktree。
- **非 Git 项目或无法创建 worktree**：使用显式隔离的目录；若也做不到，则把冲突风险说明后串行执行。

Git worktree 是一个新的文件目录，并由同一仓库管理：多个 worktree 共用 Git 对象库和提交历史，但各有独立的工作文件、索引和当前分支。已提交的 Git 对象不会为每个 Agent 复制一份；被检出的跟踪文件会在每个工作目录中各有一份。未提交修改、未跟踪文件和忽略文件不会自动复制到新 worktree。

`for_work/`、`for_worker/` 是任务过程产物/WIP 目录，不是 Git checkout。不要把完整 worktree 放入这类可能由项目收尾流程清理的目录。

## 2. 默认位置与创建前核验

经用户授权创建项目内 worktree 时，默认放在：

```text
<project-root>/.worktrees/<task-id>/<worker-id>/
```

`.worktrees/` 是本地开发基础设施，不是正式成果。创建前确认它已被忽略：团队共同约定时使用项目 `.gitignore`；仅本机使用时优先加入仓库的 `.git/info/exclude`，避免无意修改共享项目配置。若项目内路径不可写、无法安全忽略或运行平台不支持嵌套 checkout，才使用项目同级目录，并记录原因。

创建前必须：

1. 记录根目录、当前分支/HEAD 和 `git status --short --branch`；保留现有脏改动，不得为建 worktree 而 reset、clean、stash 或覆盖。新 worktree 只从指定的已提交基线创建，不包含当前未提交改动。
2. 明确基线分支/提交、唯一分支名、任务/Agent、工作目录及可写范围；用 `git worktree list` 确认目标分支未被其他 worktree 占用，确认目标路径不存在。
3. 盘点资源：用 `git count-objects -vH` 查看共享 Git 对象库，并用系统文件大小工具检查工作树、最大跟踪文件、忽略目录（如 `node_modules/`、`target/`、`dist/`）、数据目录与剩余磁盘空间。区分 Git 跟踪内容、忽略/未跟踪内容、外部原始数据和可再生缓存；不要只凭 `.git` 目录大小估算整个工作区。
4. 按测得的目录/文件大小估算并发 worktree 数量的额外磁盘开销；没有测量依据时标记为未知，不臆定“创建 worktree 几乎不占空间”。

示例（分支名和基线必须先按任务确认）：

```bash
git worktree add -b feature/<task-id> ".worktrees/<task-id>/<worker-id>" <base-ref>
git -C ".worktrees/<task-id>/<worker-id>" rev-parse --show-toplevel
git -C ".worktrees/<task-id>/<worker-id>" status --short --branch
git worktree list
```

同一分支不能同时在两个 worktree 中检出。若远端分支已存在，先判断应建立跟踪分支还是使用未占用的本地分支，不要强行复用一个已被检出的分支。

## 3. 大文件、数据与依赖的处理

- **共享对象库，不共享文件副本**：worktree 不重复复制完整 Git 历史，但会检出各自需要的跟踪文件。多个 worktree 会增加工作树文件占用；大文件若在每个工作树都被检出，空间仍会相应增长。
- **大型数据**：优先指向用户指定的唯一数据根目录，并以只读方式读取；每个任务只把自己的结果写到独立输出目录。禁止为方便并行而复制、移动、清理或覆盖原始数据。
- **大型跟踪目录**：若任务只需仓库的一部分，可在核实测试/构建依赖后采用 cone-mode `git sparse-checkout`，只检出需要的目录。稀疏检出减少工作树物化文件，不会自动删掉现有仓库共享对象库中的历史对象。
- **Partial clone**：`--filter=blob:none` 主要用于新建且服务端支持过滤的克隆；它不是在已完整下载的仓库中创建 worktree 后自动回收对象的办法。不要为了单个任务擅自改造现有克隆或远端配置。
- **大二进制资产**：只有项目明确采用并授权时才引入/迁移 Git LFS 或对象存储；先核实 LFS 对象、下载与检出行为。不要自动重写历史。即使使用 LFS，实际需要的资产在各工作目录中的检出仍可能占空间。
- **依赖、数据库和构建缓存**：新 worktree 不会带入被忽略的 `node_modules/`、虚拟环境、数据库或构建目录。优先复用包管理器的内容寻址缓存；依赖安装遵循项目安装授权。不要直接复制大型依赖树，也不要让并发 Agent 共用可变的 `node_modules/`、数据库或构建输出；为并行服务分配独立端口和数据文件。
- **超大源码文件**：如果所有工作者都必须检出同一个大型源码文件，worktree 仍会复制该文件并且不能避免合并冲突。能拆分时先按职责模块化；否则串行修改该文件，不用并发来制造冲突。
- **磁盘预算不足**：减少并发 worktree 数、采用稀疏检出，或改为串行复用一个 checkout。不要用硬链接/目录联接把可写源码或构建产物伪装成独立副本；一个 Agent 的写入可能影响另一个工作区。

## 4. 验收、交接与清理

派发单及交接件应记录 worktree 绝对路径、分支、基线 commit、工作树状态、资源隔离方案、真实测试命令和结果。管理员独立复核分支差异和测试后再决定如何集成；worktree 不会自动避免同一文件的逻辑冲突。

工作完成后不得自动删除目录或分支。先核验 `git status --short --branch`、未提交变更和未推送提交，再按用户授权使用 `git worktree remove <path>`。不得用项目 closeout 清理规则或 `rm -rf` 删除 worktree；不得自动删除其分支、提交或推送。任何封装脚本的 `remove` 行为都必须遵守同一授权边界；脚本若把目录移除与分支删除绑定在一起，按其实际影响整体视为删除目录和分支的操作。
