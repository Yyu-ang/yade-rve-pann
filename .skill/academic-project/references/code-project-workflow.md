# 纯代码开发参考工作流 (`code_project`)

本工作流适用于常规软件交付：应用程序、代码库、CLI 工具、Web 服务、自动化脚本、集成工具与可维护组件。它**不包含**学术研究问题、文献调研、实验设计、统计假设、学术图表或论文文稿的编写要求。

项目记忆契约依然生效：代码仓库本身与 `README.md` 是产品行为的最高事实来源；`PROJECT_DASHBOARD.md` 呈现用户需求闭环与交付物；`WORKLOG.md` 和 `.project-memory/` 记录持久范围、架构决策、验证证据与交接状态。

---

## 1. 入口与基线确认

1. 遵循核心启动协议：定位根目录；读取 `AGENTS.md`、`PROJECT_DASHBOARD.md`、`README.md` 与 `WORKLOG.md`；解析唯一记忆根目录；运行 `project_preflight.py`。
2. 改动代码前必须完成审查：仓库状态、根目录规范（`AGENTS.md`、`CONTRIBUTING.md` 等）、依赖清单/锁文件、源码结构、测试套件、CI 配置以及相关的现有模块。
3. 在 `WORKLOG.md` 和 `workflow/code_project/implementation_log.md` 记录基线：当前分支/Commit、工作树是否干净、可用检查工具、未决的环境限制。
4. 严禁仅为了建立基线而私自重置、清理工作树、提交 Commit、安装未声明依赖、修改构建文件或更改部署配置。涉及此类操作须提前征求用户确认。
5. 若有多个 Agent 获准并行修改本地代码，为每个并发写入者安排独立 Git 分支与 worktree；在派发前记录实际路径、基线 commit、资源策略，并检查大型跟踪文件/数据/依赖的工作树占用。不要把“不同分支”误当作“不同目录”。执行平台已提供独立工作树时只需核验，不要再嵌套创建。操作细则见同目录 `git-worktree-resource-isolation.md`。

---

## 2. 定义产品范围与验收标准

在范围尚未明确前，先完成 `product_scope.md`。必须明确：
- 目标用户/解决的问题，以及预期的交付物形式；
- 范围内明确支持的行为，以及显式的非目标（Non-goals）；
- 可观察、可测试的功能性与非功能性验收标准；
- 外部接口、兼容性约束、安全/隐私边界，以及仍需用户决策的事项。

仅指明实现机制的指令不等于完整的产品需求。保留用户的原始诉求表达；将实现路径选择单独标注。在动手编写大规模修改前，先行澄清重大歧义。

---

## 3. 按比例审查与架构设计

- 优先沿用仓库已有的语言版本、包管理工具、测试框架、格式化工具、Lint/类型检查工具以及架构风格，除非用户授权调整。
- 改动代码前，追踪每个被修改符号的定义及其全部调用方。严禁凭空臆造 API、配置项、环境变量或依赖包。
- 对于非琐碎改动，在 `architecture.md` 中更新组件边界、数据与控制流、接口契约、兼容性方案以及被否决的备选方案。
- 在 `delivery_plan.md` 中将工作拆解为小步、可独立验证的增量。每个增量均应具备明确的改动边界、验收条件、验证命令或观察方式，以及回滚/恢复说明。

---

## 4. 小步增量实现

针对每个计划中的增量：
1. 编辑前立即重读受影响代码及其局部说明文件。
2. 做出满足验收条件的最小连贯修改；避免不相关的代码重构与格式化抖动。
3. 行为变更时补充或更新针对性测试。不得编写仅机械镜像错误实现而未断言用户可见行为或契约行为的无效测试。
4. 优先运行范围最精准的检查，再运行仓库要求的大范围检查。在 `implementation_log.md` 中记录执行命令、退出码与真实输出。
5. 若检查失败，诊断根本原因，并排查同类缺陷是否出现在关联调用路径中。严禁通过削弱测试断言或吞掉异常来掩盖失败。

不得因文件已写入、Subagent 返回成功或服务已启动就宣称实现完成。完成必须建立在可观测的行为证据或测试通过证据之上。

---

## 5. 质量、兼容性与发布门禁

在交付实质性变更前，对照 `quality_release.md` 进行审查：
- 单元测试、集成测试、端到端测试或回归测试；
- Lint、代码格式、静态类型检查、构建与打包检查；
- 手动验收路径与异常/边界处理验证；
- 配置迁移、API 演进与向后兼容性验证；
- 涉及性能、并发与资源消耗时的压力或指标评估；
- 安全审查：输入校验、鉴权边界、敏感信息处理、依赖供应链与日志合规。

未执行或环境不支持的检查项应如实记为局限，不得虚假标记为通过。局部小测试通过不等于全局发布就绪。

---

## 6. 文档、交付与多 AI 协同收尾

1. 仅在变更导致内容过时的情况下更新用户文档、配置示例、API 注解及发布日志。
2. **多 AI 协作分工**：
   - **工作者角色 (Worker)**：不直接更新全局看板；向管理员提交标准化的《工作者交付汇报》，声明交付的代码路径、测试命令、退出码与验证证据。
   - **管理员角色 (Admin)**：验收工作者交付物，提炼需求闭环状态并登记至 `PROJECT_DASHBOARD.md`，追加 `WORKLOG.md`，更新 `progress/current_status.md`。
3. 运行 `project_finish_check.py --started-at <unix_ts> --json` 执行门禁检查；若确系无项目变更的纯审查任务，使用 `--no-project-change`。
4. 最终回复明确汇报：交付的行为、精确改动文件列表、执行的检查命令与结果、已知局限及下一步决策。
5. **公开发布**：需要向开源社区、应用市场或公开仓库发布纯净版本时，运行 `project_release.py` 生成干净分支或导出无 AI 脚手架的发布包。

## `code_project` 模板职责一览

| 文件 | 职责定位 |
|---|---|
| `product_scope.md` | 产品目标、功能边界、验收标准与待决事项 |
| `architecture.md` | 关乎长期维护的关键架构与接口决策 (ADR) |
| `delivery_plan.md` | 小步可验证增量计划、依赖关系、风险与完成条件 |
| `implementation_log.md` | 实际代码修改与验证命令执行的追加式证据日志 |
| `quality_release.md` | 质量门禁、兼容性/安全审查与交付就绪检查表 |

## 常见失误与规避指引

- **混淆类型**：把 `code_experiment` 当成常规编码流程 → 除非需要科研实验记录与学术结论支撑，否则常规软件开发一律使用 `code_project`。
- **盲目动手**：未深入阅读仓库代码、说明文档、依赖清单和调用链路就直接凭任务标题写代码 → 必须先审查后修改。
- **虚假凭证**：把命令已启动、后台任务返回或模型自己的陈述当作成功证据 → 必须捕获命令退出状态并实际观测输出结果。
- **随意发明命令**：用凭空想象的通用命令替代仓库已有的测试/构建脚本 → 严格使用仓库原生配置的命令。
- **夹带重构**：修复 bug 或开发特性时夹带大面积无关格式调整或代码重构 → 保持窄小、清晰、易于 review 的改动边界。
- **擅自越权**：自动执行 git commit、push、安装全局包或对外发布 → 涉及外部、持久或不可逆的操作必须取得用户明确授权。
